## 🎯 1. В чём смысл задачи?

В любой многопользовательской системе (ОС, база данных, файловый сервер) нужно решать один вопрос:
**может ли пользователь S сделать действие A с объектом O?**

**Дискреционная** (избирательная) модель отвечает на него с помощью **матрицы доступа**:
* строки — **субъекты** (пользователи),
* столбцы — **объекты** (файлы, документы),
* в ячейке `M[s, o]` — набор прав субъекта `s` к объекту `o`.

«Дискреционная» значит, что права раздаются **по усмотрению** (*discretion*) владельца/администратора:
кому захотел — тому и выдал. Так устроены права NTFS в Windows и `rwx` в Linux.

### Модель Харрисона-Руззо-Ульмана (HRU)
HRU формализует матрицу доступа и описывает, **как она меняется**. Состояние системы = матрица `M`.
Изменять её можно только шестью примитивными операциями:

| Операция HRU | Что делает | Где в программе |
| :--- | :--- | :--- |
| `enter a into M[s,o]` | выдать право | выбор значения в ячейке редактора |
| `delete a from M[s,o]` | отобрать право | выбор `0` в ячейке редактора |
| `create subject s` | добавить пользователя | кнопка «+ Пользователь» |
| `destroy subject s` | удалить пользователя | ✕ в строке пользователя |
| `create object o` | добавить объект | кнопка «+ Объект» |
| `destroy object o` | удалить объект | ✕ в заголовке объекта |

Из этих операций собираются **команды** вида `if a ∈ M[s,o] then op1, op2, …`.
В нашей программе роль такого условия играет `P[I, 0] = 1`: только пользователь с админ-правом
может выполнять операции над матрицей.

**Главный теоретический результат HRU:** вопрос «может ли право `a` когда-нибудь утечь в ячейку,
где его не было?» (*проблема безопасности*) **в общем случае алгоритмически неразрешим**.
Разрешим он только для частных случаев: моно-операционных систем (каждая команда — одна операция),
монотонных (без `delete`/`destroy`) и т. п. Это главный недостаток дискреционных моделей —
доказать безопасность системы нельзя. Его и закрывает модель из лабы №4.

### Что делает программа
1. В списке **1** выбирается пользователь `I`. Если `P[I,0] = 0`, кнопка **2** («Редактировать права доступа») серая.
2. В списке **3** выбирается объект `J`, и по ячейке `P[I, J]`:
   * `0` — поле **4** недоступно, значение **не выводится**;
   * `1` — значение выводится, но поле недоступно (только чтение);
   * `2` — значение выводится, поле доступно; всё, что напечатано, сразу записывается в `Object[J]`.
3. Кнопка **2** открывает модальную форму с матрицей `P`, где можно добавлять/удалять пользователей и объекты
   и менять права. Внизу главного окна строка состояния показывает, какая ячейка `P` сработала.

Дополнительно: программа не даёт удалить или лишить прав **последнего администратора**,
иначе матрицу больше никто не смог бы изменить.

## 📋 2. Переменные

| Переменная | В методичке | Смысл |
| :--- | :--- | :--- |
| `Users` | `Users[N]` | Имена пользователей (субъекты) |
| `Object` | `Object[M]` | Значения объектов (строки) |
| `object_names` | — | Подписи объектов в списке 3 |
| `P` | `P[N, M+1]` | Матрица доступа. `P[i][0]` — админ (0/1), `P[i][j]` — права к объекту `j-1` (0/1/2) |
| `MainForm` | форма | Главное окно (элементы 1–4) |
| `MatrixEditor` | форма редактирования | Окно редактирования матрицы |

Начальная матрица:

| | Адм. | Объект 1 | Объект 2 | Объект 3 |
| :--- | :-: | :-: | :-: | :-: |
| Администратор | 1 | 2 | 2 | 2 |
| Иванов | 0 | 1 | 2 | 0 |
| Петров | 0 | 0 | 1 | 2 |
| Сидоров | 1 | 1 | 0 | 1 |

Что стоит показать преподавателю: Иванов не видит Объект 3, Петров не видит Объект 1,
Сидоров — администратор матрицы, но сам ничего редактировать не может (админ-право и права
к объектам — разные вещи). Сидоров может выдать себе права — это и есть пример того,
почему в HRU безопасность нельзя гарантировать.
